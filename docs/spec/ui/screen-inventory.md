# 想定画面一覧・画面遷移

## このページの使い方

UI・画面設計を進めるため、想定する画面を22項目に整理します。**すべてを実装する決定ではありません。** 全画面、HUD、会話パネル、同じ画面のタブなど、Playerが見る情報と行う操作のまとまりを「画面」として登録しています。画面IDは資料を対応付けるためのもので、Scene名・クラス名・制作順を指定しません。

ラジクジラと拠点のコンセプト画は、今回の画面検討に使う参考絵として一旦完成扱いにします。画像中の比率からゲーム内寸法やUIの位置を確定しません。

画面の情報配置・見た目はUI・画面設計担当が進め、Gameplayの意味や遷移条件は各機能の正本に従います。個人の割当・期限・進捗はチーム内の管理先で扱います。

本ページは画面の仕様・候補と未決事項を記載します。**作業範囲・成果物・完了条件は次のタスクページを正とします。** 一覧や図が存在することと、関係者レビュー・タスク完了は別に確認します。

| 確認する内容 | 正となるタスク |
|---|---|
| 画面一覧・分類の確定 | [PB-TASK-0026](/tasks/ui/pb-task-0026) |
| 完成版・プロトタイプの遷移の確定 | [PB-TASK-0047](/tasks/ui/pb-task-0047) |
| 初回ラフの対象ID・制作順・記録項目 | [PB-TASK-0048](/tasks/ui/pb-task-0048) |
| 共通Resultの状態別詳細・Focus・操作lock | [PB-TASK-0022](/tasks/ui/pb-task-0022) |

各行の表示情報や操作は、既存仕様から画面化するための候補です。ボタン、数値欄、独立画面をすべて追加する指示ではなく、ラフで必要性とまとめ方を確認します。

## 対象範囲の読み方

| 対象範囲 | 意味 |
|---|---|
| プロトタイプ必須 | 既存の完成条件・接続仕様で必要な表示。仮UIでよい |
| プロトタイプ任意 | プロトタイプへ含めるか未決。必須の開始経路へ追加しない |
| 本編設計対象 | 確定した拠点機能・行動設定などを画面化する検討対象。独立画面の採用や全機能の実装時期は未決で、Battleプロトタイプには含めない |
| 完成版候補 | 将来の利便性やゲーム全体の構成から挙げた案。採用・仕様は未決 |
| 保留 | 元の機能の採否から未決。現時点でラフ作成を必須にしない |

## プロトタイプの画面

| ID・対象 | 画面・形態案 | 目的・主な表示 | 入口 → 主な操作 → 出口 | 状態差分・未決事項 |
|---|---|---|---|---|
| UI-001／必須 | [Battle画面・HUD](./battle-hud.md)／ゲーム画面上の表示 | 戦況と次の操作を判断する。HP・Stamina、照準・対象、Charge、AttackEventの予告など。Mode／Conductは対応段階で追加 | Battle開始 → 既存の移動・照準・Charge・攻撃・パリィ操作 → 共通Result。Pauseは採用時のみ | 通常、対象なし、Charge中、操作不可、Mode／Conduct追加時。情報配置、表示量、世界内表示との分担は未決 |
| UI-002／必須 | 共通Result／Clear・Game Overの状態違い | Gameが確定した結果と、次にできる操作を知らせる | Battle終了 → cleanup完了後に、ClearはContinue、Game OverはRetry → Gameの遷移先 | 表示直後の操作lock、操作可能、決定後のlock。Clear／Game Overを別システムにしない。詳細は既存UI正本と[PB-TASK-0022](/tasks/ui/pb-task-0022) |
| UI-003／必須 | 必須機能失敗・再起動案内／専用表示またはOverlay | 必須準備・cleanupの失敗時に、機能・段階・短い理由と終了・再起動の案内を表示する | Gameから中断通知 → 案内を確認 → Playerがアプリを終了・再起動 | 通常のGame Overではない。cleanup完了を待たずに表示し、Retry／Continueで中断を解除しない。専用画面かOverlayか、終了ボタンを設けるかは未決 |
| UI-004／任意 | 起動・読み込み・準備中表示／共通の待機表示 | 準備や遷移を待っていることを知らせる | 起動・Retry等の準備開始 → 待機 → 準備成功でBattle、必須準備の失敗はUI-003 | 準備処理そのものは必須だが、独立したロード画面は未確定。進捗率・取消操作・待機文言は未決 |
| UI-005／任意 | Pauseメニュー／Overlay | 中断中であることを示し、ゲームへ戻れるようにする | 採用時のPause入力 → 再開 → 元のBattle等 | 採用場面と項目は未決。Pause採用時は既存の停止契約に従う。設定・拠点帰還・Stage中のMode構成編集を勝手に追加しない |
| UI-006／任意 | 操作説明・チュートリアル案内／Overlayや説明パネル | 操作方法、今行うこと、操作結果を説明する | 表示条件または説明操作 → 読む・閉じる → 元の場面 | プロトタイプでは配布物の操作説明でもよく、ゲーム内の専用画面は任意。本編の最初のチュートリアルでラジクジラは既定の追従を使用。表示順・再表示・停止の有無は未決 |

UI-001は「バトルHUD」の既存ページを使います。新しい同名ページを作りません。UI-002の状態別詳細は既存のPB-TASK-0022で扱い、本一覧のためにResult設計を重複作成しません。

|---|---|---|---|---|

| UI-104 | Stage選択・出発準備 | 行き先と、確認すべき準備内容を判断する | 受注後または未決の出発導線 → 行き先確認・出発・戻る → 準備処理を経てBattle、または呼出元 | クエスト受注とStage選択を一つにするか、設定の確認範囲、出発条件は未決。別のStage一覧画面を必須にしない |

| UI-110 | 演奏中の画面・最小HUD | ラジクジラの単独自動演奏を鑑賞し、終了して再び始められるようにする | 広場で演奏開始 → 鑑賞・終了・再開始 → 準備状態／拠点 | 開始前／演奏中／終了後。曲名・進行表示、UI非表示、カメラ操作は未決。演奏中の継続操作、共有、採点は必須にしない |
| UI-111 | ラジクジラの行動パターン設定 | 用意された行動の順番と、各区間の継続小節数を設定する | **ストーリークリア後**、未決の設定入口 → 並び・小節数を編集 → 呼出元／演奏準備 | 未解放／編集可能、設定不足等。未解放時は既定追従で遊べる。初期から編集を要求しない。追加パターン、上限、保存方法、解放前に項目を見せるかは未決 |

## 画面遷移

### プロトタイプ

```text
起動
  ↓
Battle準備（UI-004の待機表示は任意）
  ↓
UI-001 Battle画面・HUD
  ↓ Gameが結果を確定・Gameplay入力を停止
UI-002 共通Result（表示開始・操作lock）
  ↓ Gameから必須cleanup完了・操作解禁の通知
  ├─ Clear：Continue → 決定後lock → Gameが定める受け先（具体先は未決：Q-01）
  └─ Game Over：Retry → 決定後lock → 新しいBattle準備 → UI-001

Battle準備中、または結果確定後の必須cleanupで失敗を検出
  → Gameが中断 → UI-003 中断・再起動案内（全cleanup完了を待たない）
  → Playerがアプリを終了・再起動 → 起動から新しいBattle準備
  ※ Continue／Retryは受け付けず、遅い成功通知でも中断を解除しない

UI-005 Pause・UI-006 操作説明は、採用した場合だけ元画面に重ねる
```

**未決：プロトタイプでClear後のContinueが到着する具体的な受け先（Q-01）。** UI正本では拠点／Stage選択へのrouteですが、プロトタイプの完成条件はその実画面を対象外としています。企画・Game・UI設計で、Continueのroute接続を実装する前に具体化します。図と概要ラフでは「Gameが定める受け先・未決」と記載できます。拠点画面を新たに必須化せず、ClearにRetryを追加して解決することもしません。

Resultの表示開始はcleanup完了を待つ必要がありません。待つのは操作解禁です。詳細な状態・Focus・入力gateは[UI正本](/spec/ui/)と[PB-TASK-0022](/tasks/ui/pb-task-0022)を参照します。図中の起動、準備、中断、操作lockは処理・状態であり、追加の画面IDを表しません。

### 完成版：本編・拠点の構成案

以下の線は導線の検討案です。施設の入口や、画面を開く順番の実装確定を意味しません。

```text
ゲーム開始（UI-201の採用・本編開始地点は未決）
  ↓
UI-101 拠点の探索画面
  ├─ UI-102 NPC・受付との会話 → 終了 → UI-101
  │    └─ UI-103 クエスト一覧・詳細・受注 → 閉じる → 呼出元
  ├─ 掲示板 → UI-103 クエスト一覧・詳細・受注
  │                 └─ UI-104 Stage選択・出発準備 → Battle準備 → UI-001
  ├─ 調律工房 → UI-105 Mode構成／UI-106 Conduct設定 → 閉じる → UI-101
  ├─ UI-107 試走スペース → 終える → 拠点／工房（Q-05）
  ├─ UI-108 レコード販売所 → 閉じる → UI-101
  └─ 演奏広場 → UI-109 演奏準備 → UI-110 自動演奏・鑑賞
                                    └─ 終了 → UI-109 準備状態へ

UI-103の呼出元：UI-102の会話、またはUI-101の掲示板（戻り方はQ-03）
UI-104で出発せず戻る → 呼出元（受注との統合・出発条件はQ-03）
UI-109を閉じる → 呼出元／UI-101（入口と終了後の戻り方はQ-07）

UI-111 行動パターン設定
  └─ ストーリークリア後に編集解放
     入口の施設・メニュー、UI-109と統合するかは未決
  └─ 編集を終える → 呼出元／UI-109（接続・保存の扱いはQ-07）

UI-001 → Gameが結果確定 → UI-002 共通Result（操作lock）
  Gameから操作解禁の通知後：
  Clear → Continue → 決定後lock → UI-101 拠点／UI-104 Stage選択
  Game Over → Retry → 決定後lock → 現在Stageの新しいBattle準備 → UI-001
```

会話・施設メニューを閉じた場合の基本案は呼出元へ戻ることです。図の工房・掲示板・演奏広場はUI-101内の施設・場所を表し、別画面の追加ではありません。UI-111の入口は未決のまま残し、UI-109から必ず開く線は確定しません。操作中の未保存変更、購入や出発などの確定操作、演奏中の終了については、[未決事項](#open-questions)の確認先と決定時点に従って戻り方を具体化します。

## 画面ではなく共通部品として検討するもの

- ボタンの通常・Hover・Focus・押下・使用不可の表示。
- タブ、一覧と詳細、説明文、操作キーの案内。
- 内容確認・変更取消等の確認ダイアログ。どの操作に確認が必要かは各画面で決める。
- 通知・簡潔なフィードバック。専用の全画面へ遷移するかは内容に応じて判断する。
- データなし、未解放、準備中、読込失敗等の状態表示。

これらを一律に独立画面として数えません。通常の「操作できない」表示を、UI-003のシステム中断として扱うこともしません。

## ラフ制作と記録

制作する画面の範囲と順番は[PB-TASK-0048の制作順](/tasks/ui/pb-task-0048#rough-order)、提出する情報は[同タスクの記録項目](/tasks/ui/pb-task-0048#rough-record)を参照します。UI-001の情報・状態の参照先は[バトルHUD](./battle-hud.md)です。仕様ページに個人の進捗や完了判定を重複して記録しません。

## 未決事項

各画面の行にある未決事項を、次の確認先へつなぎます。「決定が必要な時点」は仕様上の依存関係で、個人の期限は内部管理先へ記録します。未決事項を残して遷移やラフを確認する場合も、対象ID、未決の内容、確認先を文章に併記します。

- **Q-01／UI-002**：プロトタイプのClear後のContinue受け先。
  確認先・参照仕様：企画・Game・UI設計。[Game](/spec/game/)、[UI](/spec/ui/)、[プロトタイプ](/spec/game/prototype)。
  決定が必要な時点：Continueのroute接続を実装する前。
  継続できる検討範囲：未決の受け先を明示した遷移図・概要ラフ。ClearはContinueだけ。UI-001の通常HUDへ影響しない。

- **Q-02／UI-001**：HUD／世界内表示の分担、ChargeとAttackEventの表示量、Mode／Conduct追加時の差分、仮色・文言等。
  確認先・参照仕様：UI設計・Player・Charge／Allocation・BGM・Camera担当。[バトルHUD](./battle-hud.md)と同ページの機能正本。
  決定が必要な時点：レイアウトを詳細設計へ渡す前。通知・入力の接続はUI実装前。
  継続できる検討範囲：1920×1080・Keyboard／Mouseの配置比較。通常Charge→発射→浄化とMode／Conduct追加段階を分ける。

- **Q-03／UI-101～104**：施設を開く条件、会話・受付と掲示板の共用、受注・出発の統合、戻り先、確定操作、依頼解放・報酬・受注数。
  確認先・参照仕様：企画・Game・UI設計。[拠点](/spec/hub/)、[入力](/spec/player/input-and-controls)。
  決定が必要な時点：依頼・会話・出発の遷移と詳細操作を実装する前。
  継続できる検討範囲：既知の目的・情報の配置と、呼出元へ戻る基本案。未決の報酬・通貨・解放条件は確定欄にしない。

- **Q-04／UI-105・106**：工房のConduct設定範囲、Mode／Conductをまとめるか、保存・適用・取消、未解放時の表示。
  確認先・参照仕様：企画・Player機能担当・UI設計。[Mode構成](/spec/player/mode-configuration-and-effectors)、[Mode／Conduct](/spec/player/player-action-mode-change-and-conduct)。
  決定が必要な時点：設定項目・保存操作の詳細設計前。
  継続できる検討範囲：Mode 1編集不可、Mode 2～4最大3スロット等の既存契約。未決のConduct装備数・保存方式を描き足さない。

- **Q-05／UI-107**：試せる機能、専用UIの要否、開始・終了・拠点／工房への戻り方。
  確認先・参照仕様：企画・試走機能担当・UI設計。[拠点](/spec/hub/)。
  決定が必要な時点：試走の開始・終了導線と詳細UIの決定前。
  継続できる検討範囲：試す／終える目的と見通しの比較。Battle HUD流用・採点・DPSは採用済みにしない。

- **Q-06／UI-108・109**：商品・購入・所持・演奏利用の関係、価格・通貨、購入不可、選曲・音源取込。
  確認先・参照仕様：企画・販売／演奏機能担当・UI設計。[拠点](/spec/hub/)、[演奏広場](/spec/hub/performance-plaza)。
  決定が必要な時点：購入・選曲の詳細設計とデータ接続前。
  継続できる検討範囲：商品・曲の情報領域を比較。実価格・通貨・所持ライブラリは未決と明記。

- **Q-07／UI-109～111**：演奏準備・行動設定の入口、統合、戻り先、保存、演奏終了時の戻り方、鑑賞の解放時期、曲進行・設定列の上限。
  確認先・参照仕様：企画・Game・演奏／ラジクジラ担当・UI設計。[演奏広場](/spec/hub/performance-plaza)、[行動設定](/spec/radiowhale/behavior-patterns)。
  決定が必要な時点：入口・終了・保存・解放判定の実装前。
  継続できる検討範囲：自動演奏と鑑賞、既定追従、ストーリークリア後の行動設定編集。鑑賞の解放を同じ条件に固定しない。

- **Q-08／UI-003**：専用表示かOverlayか、終了ボタンの要否、短い理由と案内の見せ方。
  確認先・参照仕様：Game・UI設計／実装。[必須機能失敗方針](/spec/common-technology/feature-connections#failure-policy)。
  決定が必要な時点：中断UIの詳細設計前。
  継続できる検討範囲：機能・段階・理由と終了／再起動案内。Game Over化、Continue／Retryでの復旧はしない。

- **Q-09／UI-004～006**：待機表示・Pause・操作説明の採否、表示条件、項目・文言。
  確認先・参照仕様：企画・Game・UI設計。[プロトタイプ](/spec/game/prototype)、[入力](/spec/player/input-and-controls)。
  決定が必要な時点：採用と後続制作範囲を決める時点。
  継続できる検討範囲：任意経路として一覧・図へ記録。準備処理の必須性と専用ロード画面を区別する。

- **Q-10／UI-201～204**：タイトル等の採否、入口・戻り先、設定項目、保存方式、クレジット内容。
  確認先・参照仕様：企画・Game・UI設計／各機能担当。
  決定が必要な時点：完成版の採用判断・後続詳細設計前。
  継続できる検討範囲：候補の目的・未決項目の整理。プロトタイプの開始経路へ追加しない。

- **Q-11／UI-301・ID未付与項目**：機能の採否、目的・情報・操作・戻り先・状態差分の具体化。
  確認先・参照仕様：企画・各機能担当。[拠点](/spec/hub/)、[演奏広場](/spec/hub/performance-plaza)。
  決定が必要な時点：機能を採用する時点。
  継続できる検討範囲：保留・対象外理由の維持。採用前のラフ・実装を必須にしない。

全IDに共通する独立画面・タブ・Overlay・世界内表示の選択、閉じる操作、仮文言・仮色・仮Iconは、各項目の機能担当とUI設計／実装で詳細設計前に確認します。この一覧は確認すべき内容を整理するもので、機能の採用や新しい遷移先を決定するものではありません。
