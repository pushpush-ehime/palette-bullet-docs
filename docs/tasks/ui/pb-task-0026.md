# PB-TASK-0026｜想定画面一覧・画面遷移・ラフ下絵作成

## タスクの目的

Palette Bulletで想定される画面を一度一覧化し、完成版とプロトタイプの対象範囲を区別したうえで、画面同士のつながりと大まかな情報配置を確認できるラフ下絵を作成します。

このタスクでは最終デザインを決めません。仕様に書かれていない内容を下絵だけで確定せず、画面制作や実装を始める前に決める必要がある項目を発見し、関係者が相談できる状態にすることを目的とします。

画面の初回一覧と導線案は[想定画面一覧・画面遷移](/spec/ui/screen-inventory)を参照します。以後は同じ画面IDで内容を更新し、ラフ画像と状態差分を追加します。一覧の追加だけでは、本タスクの下絵制作・レビュー・実装は完了していません。

## 完成時にできるようになること

- ゲーム全体で必要になりそうな画面と、その目的を一覧で確認できる
- プロトタイプに必要な画面と、完成版でのみ必要な画面を区別できる
- 画面間の入口、出口、戻り先を画面遷移図で確認できる
- プロトタイプ対象画面の構成を1920×1080基準の下絵で相談できる
- UIの個別ワイヤーフレームや実装タスクを、重複なく切り出せる
- 仕様へ追記すべき未決事項を把握できる

## 実施内容

### 1. 想定画面を洗い出す

少なくとも次の候補を起点に、ゲーム内画面、Overlay、Menuを洗い出します。候補にない画面が必要だと判断した場合は追加し、不要と判断した候補には理由を記載します。

- 起動・ロード
- タイトル／ゲーム開始
- 拠点
- ステージ選択・Battle準備
- Battle画面／HUD
- Pause
- Clear／Game Over共通Result
- 必須機能失敗時の中断・再起動案内
- 操作説明
- 設定

各画面には、少なくとも次を記載します。

| 項目 | 記載内容 |
|---|---|
| 画面ID・画面名 | 資料間で同じ画面を識別できる名称 |
| 目的 | Playerがこの画面で確認・実行すること |
| 対象範囲 | プロトタイプ必須／プロトタイプ任意／本編設計対象／完成版候補／保留・対象外。施設・機能の採用と独立画面の採用は区別する |
| 入口 | どの状態・操作から表示されるか |
| 出口 | どの状態・画面へ進むか |
| 主な表示情報 | Playerの判断に必要な情報 |
| 主な操作 | Keyboard／Mouseで必要な操作 |
| 状態差分 | Loading、Empty、Locked、Error等の有無 |
| 未決事項 | 仕様確認や判断が必要な内容 |

### 2. 画面遷移図を作成する

次の2系統を混同しないように作成します。

1. 完成版で想定される`ゲーム開始 → 拠点 → ステージ選択・準備 → Battle → Result → 次の行き先`の遷移
2. プロトタイプの`起動 → 検証用Battle → 共通Result`に対する、`Game Over → Retry → 新しいBattle準備`と`Clear → Continue → Gameが定める受け先`の遷移。Clear後のプロトタイプ上の具体的な受け先は、画面一覧の未決事項としてGame側と確認する

Pause等、プロトタイプで実装するか未確定の画面は、必須経路へ暗黙に含めず、任意または未決として表現します。

必須の準備・cleanup失敗時の中断案内は、通常のGame Over／Retryと区別して図示します。[共通接続仕様D03](/spec/common-technology/feature-connections#failure-policy)に従い、画面内のRetryで復旧する導線は追加しません。

### 3. ラフ下絵を作成する

一覧のうちラフ作成の対象にした画面について、レイアウトの方向性が分かる低解像度の下絵を作成します。保留・対象外の項目は、判断理由を記録したうえでラフ作成を必須にしません。

- 完成版候補の画面は、情報量と主要操作が分かるThumbnailまたは手描き相当のラフでよい
- プロトタイプ必須画面は、1920×1080を基準に主要情報、主要操作、画面端の安全域が分かるラフにする
- Battle画面は、仮HUD、照準、選択・Charge・攻撃に必要な情報の配置候補を示す
- 共通Result画面は、本タスクでは遷移図上の位置と概要ラフまでとし、状態別の詳細はPB-TASK-0022へ委ねる
- 仮文言、仮Icon、仮色は、確定仕様と誤認されないように注記する

### 4. 未決事項と後続タスクを整理する

下絵の作成中に見つかった仕様不足を、重要度と確認先が分かる一覧にします。高解像度のWireframe、HUD詳細設計、個別Menu設計、Runtime実装等は、画面単位で後続タスク候補として整理します。

### 5. 関係者レビューを行う

企画、デザイン、プログラム担当でレビューし、少なくとも次を確認します。

- 画面の漏れや重複がないか
- 完成版とプロトタイプの境界が仕様と一致しているか
- プロトタイプの主要フローを途中で止める不足画面がないか
- 実装前に決める必要がある項目を拾えているか

## 対象範囲

- ゲーム内画面、Overlay、Menuの一覧
- 完成版候補とプロトタイプ対象の区別
- 完成版とプロトタイプの画面遷移図
- 各画面の低解像度ラフ下絵
- 1920×1080基準のプロトタイプ画面ラフ
- 仮文言、仮Icon、仮色
- 未決事項と後続タスク候補の一覧

## 対象外

- 最終品質のUIデザイン
- Logo、Font、Icon、色、Animation、VFXの最終決定
- UI Toolkit／uGUI等によるRuntime実装
- PB-TASK-0022が担当するResult画面の状態別詳細Wireframe
- ゲームパッド用のFocus移動設計
- 入力割当の変更機能
- 完成版の拠点、ステージ選択、設定画面の実装
- 仕様で未確定のGameplay情報や数値の独自決定

## 完了条件

- [ ] 想定される画面に画面ID、名称、目的が付与されている
- [ ] 各画面がプロトタイプ必須／任意／本編設計対象／完成版候補／保留・対象外のいずれかに分類されている
- [ ] 各画面の入口、出口、主な表示情報、主な操作が記載されている
- [ ] 完成版とプロトタイプの画面遷移を区別して確認できる
- [ ] プロトタイプの起動、Battle、Clear／Game Over Result、Retryが途切れずにつながっている
- [ ] ラフ作成対象の各画面に低解像度の下絵があり、保留・対象外の項目には判断理由がある
- [ ] プロトタイプ必須画面は1920×1080基準で主要情報と主要操作を確認できる
- [ ] Battle画面でPlayerの判断に必要な仮HUD要素と照準の配置候補を確認できる
- [ ] 共通Resultの詳細設計がPB-TASK-0022と重複していない
- [ ] 仮の内容と確定済み仕様を資料上で区別できる
- [ ] 未決事項に確認先または判断担当が記載されている
- [ ] 後続のUI設計・実装タスク候補が画面単位で整理されている
- [ ] 企画、デザイン、プログラム担当のレビュー結果が記録されている

## 確認手順

1. 画面一覧をゲーム全体仕様とプロトタイプ仕様に照らして確認します。
2. 完成版とプロトタイプの画面遷移図をそれぞれ入口から終点までたどります。
3. プロトタイプ経路を`起動 → Battle → Clear Result → 次の行き先`と`起動 → Battle → Game Over Result → Retry`の両方で確認します。
4. ラフ作成対象の各行から対応する下絵を開けること、保留・対象外には判断理由が記録されていることを確認します。
5. 1920×1080基準で、プロトタイプ必須画面の主要情報と主要操作が画面外へ欠けていないことを確認します。
6. PB-TASK-0022との担当境界と、未決事項・後続タスク候補を企画、デザイン、プログラム担当が確認します。

## 前提・依存タスク

なし。Player Action／State Graph基盤やGameplay Runtimeの完成を待たず、現行仕様と仮情報で着手できます。

PB-TASK-0022は共通Result画面の状態別詳細Wireframeを担当します。本タスクの画面一覧と遷移図を共有し、Resultの詳細成果物を重複して作りません。

## 実施時の注意点

- プロトタイプは拠点やステージ選択を経由せず、Battleから直接開始します。
- 拠点、ステージ選択、詳細な設定画面をプロトタイプ完成条件へ追加しないでください。
- Pauseはプロトタイプ必須仕様ではないため、未決のまま必須経路へ追加しないでください。
- ClearとGame Overは別々の勝敗判定画面ではなく、共通Result画面のvariantとして扱います。
- 画面の見た目だけで新しいGameplay仕様や入力操作を確定しないでください。
- 未決事項を下絵から読み取らせず、文章でも明示してください。

## 提出・報告方法

1. 画面一覧、画面遷移図、ラフ下絵の元データと確認用画像をGoogle共有ストレージへ配置します。
2. Notionタスクへ共有リンク、レビュー結果、未決事項、後続タスク候補を記載します。
3. 仕様へ反映が必要な決定事項は、対象ページと追記原稿が分かる形で添付します。
