# タスクの進捗と実装・成果記録

タスクページの上部と一覧に、Notionから取得した進捗を表示します。進捗の変更はNotionで行います。
実装・成果記録はタスクのMarkdown本文に書き、GitHubのPull Requestで確認してマージします。
記録を追加してもタスクは完了になりません。完了からレビューや着手へ戻しても記録は残ります。
完了で記録がない場合は「完了」と「実装記録は未登録」の両方が表示されます。

## 記録の書き方

タスクの「このページを編集」から本文を開き、`## 実装・成果記録`の下へ、日付と段階ごとに追記します。
欄がない既存ページには見出しから追加してください。目的・実施予定・完了条件とは別に、実施した事実を書きます。

以下は**書式の見本**です。日付・段階・内容を実際の事実に置き換え、コードフェンスの外へ貼り付けます。
記入欄だけの状態や、コードブロック・引用・コメント内の見本は実装記録に数えません。

```md
## 実装・成果記録

### YYYY-MM-DD｜第1段階（途中経過）

- できるようになったこと：<確認できた結果>
- 実装・制作方法：<主要構成・判断理由・変更した場所>
- 成果物：<実装PR・Commit・資料・素材などへのリンク>
- 確認した操作・テスト・版と結果：<実施した確認と結果。未確認は未確認と書く>
- 実接続／Fake：<どこまで実物と接続したか。該当しなければ対象外と理由を書く>
- 制限・残作業・対象外：<既知の制限と残る作業。なければなし>
```

`### 日付｜段階`と6つの箇条書きを1件の記録として扱います。日付は実在する`YYYY-MM-DD`、区切りは全角の`｜`と`：`です。
6項目に内容があり、`未記入`・`未登録`・`<記入欄>`などのままでないものを「記録あり」と表示します。
まだ確認できていない項目は、例えば「未確認（実機を準備中）」と事実を書いてください。
リンクがまだ用意できない場合は理由を書けます。全タスクにコードCommitを要求しません。
資料・画像・音声などはその成果物を示し、実接続／Fakeが関係しなければその旨を明示します。

次の段階や最終結果は、別の`### 日付｜段階`と6項目を追加します。
過去の結果は進捗変更だけでは削除せず、訂正が必要なら理由が分かるように更新します。変更履歴はGitHubで確認できます。
フォームは本文全体を保存・コピーするため、担当班や関連仕様を変更しても記録は保持されます。
プレビュー上部の件数と本文の両方を確認してください。見本だけのタスクは未登録のままです。

## Codexへ依頼する例

> PB-TASK-XXXXの実装・成果記録に、第1段階の途中経過を追記してください。対象PRは〈URL〉、確認した版は〈Commit／素材の版〉、実施した確認と結果は〈内容〉です。実接続は〈範囲〉、Fakeは〈範囲〉、未確認・残作業は〈内容〉です。既存記録を残し、不明な事実は推測せず未確認としてください。Notionの進捗は変更せず、記録のPRを作成してください。

個人名・認証情報・非公開URLは記録や記入例に含めません。
PB-TASK-0018を含め、記録の追加やこの機能の導入によって既存タスクを完了扱いにはしません。

## 進捗と取得日時の読み方

「未着手・着手・レビュー・完了」はNotionの状態です。仕様ページの「確定・仮仕様・未決」などとは別です。
タスク一覧では検索・分類・Notionの進捗を組み合わせて絞り込めます。カテゴリ内でも検索と進捗を併用できます。

| 表示 | 意味 |
|---|---|
| 未連携 | 取得に成功したが、同じタスクIDの有効なNotionページがない |
| 状態未設定 | Notionページの状態が空 |
| 未知の状態 | 定義外の選択肢、またはページの状態プロパティが不正 |
| ID重複（要確認） | 同じタスクIDのNotionページが複数あり、進捗を一意に決められない |
| 取得失敗 | 取得できず、利用できる前回情報もない |
| 状態不明（未取得） | ローカル開発、取得設定なしなどで前回情報がない |
| 最新の取得に失敗・前回情報 | 前回取得できた状態。横の日時は前回成功時のまま |

取得日時は全ページを読み終えた実時刻を日本時間（JST）で示します。予定時刻やビルド時刻ではありません。
タスクIDで照合するため、同じIDを保ってカテゴリを移動すると状態も追従し、本文内の記録もファイルと一緒に移動できます。
ローカルのID重複は既存の検査で公開を停止します。Notion側の重複は既存同期では最初のページを使いますが、表示用取得では状態の誤表示を避けるため要確認とします。既存同期の選択方法は変更しません。
削除・アーカイブ済みのNotionページは日次取得では未連携になり、再作成しません。通常公開時の既存起票処理は従来通りです。
設計書から削除したタスクは一覧と生成データから除外します。IDを別のタスクへ再利用しないでください。

## 管理者向けの取得・公開経路

`Deploy VitePress site to Pages`に日次の`0 3 * * *`（毎日12:00 JST）を追加しています。
12時は取得・ビルド・公開の開始予定です。GitHub Actionsの待ち時間やビルド時間により、12時ちょうどの表示更新は保証されません。
[GitHub Actionsのscheduleの説明](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule)も参照してください。

| 実行のきっかけ | 処理 |
|---|---|
| main更新・mainからの手動公開 | 従来のNotion起票・名称／URL／担当班同期 → 前回進捗を復元 → 進捗取得 → 検査・ビルド → 公開 |
| 日次12時 | 前回進捗を復元 → 読み取り専用の進捗取得 → 検査・ビルド → 公開 |
| PR検査・通常のローカル検査 | 認証も外部接続も不要。取得ファイルがなければ状態不明のまま検査・ビルド |

日次は`notion-sync.mjs`も完了通知処理も呼びません。Discord Webhookも進捗取得ステップに渡しません。
既存Discord通知の頻度・方式と深夜送信抑制の判定は、そのまま維持します。
通常公開でも同じ取得処理を実行し、仕組みを共通化しています。

`scripts/notion-progress.mjs`は既存と同じNotion APIバージョン`2022-06-28`でDBのGETとquery POSTだけを使用します。
queryのPOSTは読み取りであり、ページ・プロパティの更新APIは呼びません。
この旧バージョンのAPIは[NotionのQuery a database](https://developers.notion.com/reference/post-database-query)を参照してください。
API世代の移行は既存同期との整合を含む別の作業です。

生成ファイルは`docs/.vitepress/content/task-progress.json`です。GitへCommitしません。
成功した取得情報だけをGitHub Actions cacheへ保存し、通常・日次で共用します。失敗時はキャッシュの元の取得日時を保ち、前回情報と明示します。
キャッシュが失効・消失・不正の場合は前回情報なしとして扱います。キャッシュ保存の失敗は公開を止めません。
公開カタログはタスクIDに対応する状態、取得日時、既存Notion URLと取得結果だけを使い、Token・担当者・Notion本文を含めません。
定義外の状態名も公開JSONへそのまま転記せず「未知の状態」とします。

公開全体は既存の`pages` concurrencyで直列実行します。キュー順や再実行で古いソースへ戻さないよう、実行開始時に最新mainを取得し、公開直前にもmainのSHAを確認します。
ビルド中にmainが進んだ場合はその公開をスキップし、次の通常公開に任せます。
取得できない場合も明示付きの前回情報または状態不明で公開できます。検査・ビルド・公開自体が失敗した場合、既存公開サイトは置き換わりません。

## 導入と検証

1. PRで`npm run docs:check`と画面表示を確認します。
2. 既存のSecrets `NOTION_TOKEN`・`NOTION_TASK_DB_ID`を確認します。日次取得に新しいSecretは不要です。
3. mainへマージすると通常公開で反映され、以降は日次でも同じ経路を実行します。
4. Actionsの`Read task progress from Notion`と公開結果を確認し、ページのJST取得日時を確かめます。

認証なしで失敗時の表示を確認するには、Notion環境変数を設定せず`npm run notion:progress`を実行します。
`npm run docs:test`は外部通信をmockへ置き換え、ページ送り・4状態・失敗・再開・記録保持を検証します。
生成ファイルを手元でfixtureに置き換える場合もGitへ追加せず、確認後は削除します。実際のタスクへ架空の成果を書かないでください。
